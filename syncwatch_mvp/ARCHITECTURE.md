# Архитектура SyncWatch

Документ описывает фактическую реализацию на момент проверки 2 октября 2026 года. Целевой сценарий SyncWatch связывает ведущий компьютер с несколькими ведомыми в локальной сети; текущая модель соединения и GUI хранит данные только одного участника. Приложение управляет локальными экземплярами VLC и позволяет передать видеофайл второму участнику. Известные нарушения ожидаемого поведения приведены в [отчёте](AUDIT.md).

## Запуск и окружение

Для приложения используйте Python 3.12, зависимости из `requirements.txt` и полный VLC runtime соответствующей архитектуры. `Role` использует `StrEnum`, поэтому Python 3.10 не подходит для запуска приложения.

Требования исправлены на `websockets>=14,<16`: `connection_manager.py` импортирует `websockets.asyncio`, а псевдонимы `websockets.serve/connect` используют эту реализацию начиная с версии 14. В тестовом окружении использован `websockets==15.0.1`. Источник: [документация перехода websockets](https://websockets.readthedocs.io/en/15.0/howto/upgrade.html).

Из каталога проекта:

```bash
cd syncwatch_mvp
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip install websockets==15.0.1
python -m src.main
```

На Windows создайте окружение через `py -3.12 -m venv .venv` и активируйте `.venv\Scripts\Activate.ps1`. Подробная настройка VLC приведена в [README](README.md), упаковка — в [BUILD](BUILD.md). Заявленные Windows и macOS в рамках этого аудита не проверялись реальным воспроизведением.

## Компоненты

| Файл или каталог | Фактическая ответственность |
| --- | --- |
| `src/main.py` | Настройка логирования и поиска VLC, создание QApplication и окна |
| `src/ui/main_window.py` | Интерфейс, состояние комнаты, загрузка медиа, команды, таймеры, передача файлов |
| `src/network/network_thread.py` | QThread с собственным asyncio loop; передача событий через Qt signals |
| `src/network/connection_manager.py` | Сервер, клиент, handshake, отправка и чтение сообщений |
| `src/network/messages.py`, `protocol.py` | Конвертация JSON и проверка версии и типа сообщения |
| `src/network/file_transfer.py` | Отправка чанков, приём во временный файл, проверка и завершение |
| `src/player/vlc_player.py` | libVLC и привязка нативного видеовывода к QWidget |
| `src/media` | Метаданные, частичный SHA-256, сравнение файлов |
| `src/session` | Роль и структура флагов готовности и метрик |
| `src/synchronization` | Формулы RTT, смещения часов и рассинхрона |
| `src/infrastructure` | Пути bundled VLC и локальный журнал |

`src/app` пока пуст. Отдельных контроллеров сессии и синхронизации нет. Функции `ClockSample`, `summarize` и `execution_delay_seconds` тестируются, но окно их не использует.

## Потоки выполнения

Qt обслуживает интерфейс и таймеры. `NetworkThread` запускает asyncio loop, вызывает обработчики WebSocket и передаёт сообщения окну через signals. `ThreadPoolExecutor(max_workers=3)` рассчитывает отпечатки и отправляет файлы.

Отправляющий worker использует `send_wait`: ждёт завершения отправки очередного сообщения, прежде чем читать следующий чанк. Принимающая сторона декодирует base64, пишет на диск и проверяет файл прямо в обработчиках окна, поэтому медленный диск способен задержать интерфейс. Отдельного ограниченного буфера между сетью и GUI нет.

## Подключение

Ведущий создаёт сервер на `0.0.0.0:45892`. Код комнаты — четыре случайные цифры, ID сессии — 8 случайных байт в hex. Ведомый вводит адрес, порт, код и имя устройства.

1. Клиент открывает `ws://IP:port` и отправляет `join`.
2. Сервер ждёт первое сообщение не более 10 секунд, проверяет тип, версию протокола и код комнаты.
3. При успехе отправляет `join_accepted` с ID сессии, иначе `join_rejected`.
4. После handshake участники читают и отправляют сообщения по тому же соединению.

TLS, ограничение попыток ввода кода и автоматическое переподключение не реализованы. Требование допускает несколько ведомых, но manager хранит один сокет: последовательное второе подключение отклоняется, а одновременные могут перезаписать текущего получателя команд. Нужны рассылка и состояние каждого участника. ID сессии после handshake не проверяется. Сервер не пересылает в окно событие `join_accepted` для себя; уже выбранное медиа не публикуется заново при подключении участника.

## Формат сообщений

Все сообщения — JSON-объекты с общими полями:

| Поле | Значение |
| --- | --- |
| `type` | Тип из `ALLOWED_TYPES` |
| `protocol_version` | Сейчас `1` |
| `session_id` | ID сессии; сейчас фактически не проверяется при чтении |
| `message_id` | UUID; дедупликация по нему не реализована |
| `sent_at` | `time.monotonic()` отправителя, секунды |

Поля payload находятся на верхнем уровне JSON. `Message.to_dict` позволяет payload перезаписать общие поля. Декодер проверяет размер до 1 MiB, JSON-объект, наличие части обязательных полей, тип сообщения и версию. Отдельных схем для каждого payload, проверки конечности чисел и правил доступа по роли нет.

`sent_at` двух машин нельзя сравнивать напрямую: монотонные часы имеют разные точки отсчёта.

| Группа | Сообщения, обрабатываемые текущим кодом |
| --- | --- |
| Подключение | `join`, `join_accepted`, `join_rejected` |
| Метрики | `ping`, `pong`, `state` |
| Медиа | `media_info`, `ready`, `media_force_match` |
| Управление | `play`, `pause`, `seek`, `sync_correction` |
| Передача | `file_offer`, `file_accept`, `file_reject`, `file_cancel`, `file_chunk`, `file_complete`, `file_error` |

`media_match` и `media_mismatch` отправляются, но окно не имеет отдельных веток их обработки: сравнение выполняется по `media_info`. Наличие `stop`, `not_ready`, `session_ended` и других типов в `ALLOWED_TYPES` не означает, что соответствующий сценарий реализован.

## Медиа и готовность

После выбора файла VLC запускается и получает команду паузы. Worker считывает размер, имя и SHA-256 трёх блоков по 1 MiB: в начале, середине и конце. Длительность опрашивается до 5 секунд; даже при результате `0` файл считается готовым.

Устройства обмениваются `media_info` и `ready`. Совпадение означает одинаковые размер и отпечаток, а также различие длительности не более 1000 мс. Это не полная проверка содержимого. «Продолжить без совпадения» может нажать любой участник; оно отключает требование совпадения, но не сопоставляет временные шкалы разных монтажей видео.

Текущий `_playback_allowed` проверяет совпадение и отсутствие передачи. Он не требует соединения или двух флагов готовности. При смене файла старая локальная информация и готовность не сбрасываются полностью до завершения worker.

## Воспроизведение и синхронизация

Локальные Play/Pause/Seek доступны ведущему. Команда содержит возрастающий `command_id`, `position_ms` и `execute_delay_ms=350`. Для Seek также передаётся `resume`. Ведущий запускает локальный таймер, ведомый запускает свой таймер после получения сообщения. Поэтому выполнение у ведомого отстаёт на время доставки сообщения.

Ведомый отбрасывает ID, не превышающий последний полученный, но уже поставленные таймеры не отменяются. Проверки поколения сессии при выполнении нет. Входящие команды также могут выполниться на ведущем.

Каждые 500 мс ведомый отправляет состояние плеера, а ведущий отправляет ping. Ведущий сравнивает полученную позицию с текущей локальной. При модуле отклонения больше 400 мс и интервале минимум 3 секунды он отправляет `sync_correction`. Возраст измерения, время доставки, будущая позиция и готовность медиа не учитываются. Проверяется отклонение позиции, но не самостоятельное расхождение состояния play/pause. Ping отображается на ведущем; ведомый сам не инициирует измерение.

## Передача видео

Любой участник с открытым файлом может нажать «Отправить файл». Получатель подтверждает предложение, после чего создаётся `.part` в `~/.syncwatch/received`.

1. `file_offer` содержит ID передачи, имя, размер, длительность и частичный отпечаток.
2. Получатель отвечает `file_accept` либо `file_reject`.
3. Отправитель читает блоки по 512 KiB, кодирует их в base64 и отправляет `file_chunk` с последовательным индексом. Получившееся сообщение укладывается в лимит 1 MiB.
4. Приёмник проверяет индекс и base64, затем пишет данные. Превышение заявленного размера обнаруживается после записи блока.
5. `file_complete` запускает сверку размера и частичного отпечатка; успешный `.part` переименовывается и открывается как локальное видео.
6. `file_cancel` и `file_error` используются для прерывания; временный файл удаляется при штатной очистке.

Полного хеша, возобновления, таймаута ожидания предложения, проверки свободного места и подтверждения успешного открытия файла отдельным сообщением нет. `_unique_path` учитывает существующие финальные файлы, но не одноимённые `.part`. После аварийного завершения такие файлы могут остаться.

## Данные и журнал

Полученные видео сохраняются в `~/.syncwatch/received`; автоматическое удаление завершённых передач отсутствует. Журнал находится в `~/.syncwatch/logs/syncwatch.log`. Сейчас явно логируются ошибки запуска и серверного обработчика; полный перечень событий playback и коррекции из старого README не реализован. Ротации журнала нет.

## Проверка изменений

```bash
cd syncwatch_mvp
python -m pytest -q -rx
python -m pytest tests/test_audit.py --runxfail -q
```

Вторая команда намеренно показывает ошибки известных дефектов. `xfail(strict=True)` в обычном запуске обозначает неисправленные требования; после исправления необходимо снять соответствующую метку. В аудите используется `websockets==15.0.1`, сетевым тестам нужен доступ к локальным сокетам.

Тесты UI извлекают методы из AST исходного класса и подставляют плеер, сеть и таймеры. Это проверка логики контроллера без импорта Qt/VLC; она не проверяет графику, сигналы Qt, native video surface или реальный тайминг декодера. План ручной проверки приведён в отчёте.
