# Архитектура SyncWatch 0.2.0-beta.1

## Компоненты

| Компонент | Ответственность |
| --- | --- |
| `src/main.py`, `src/ui/startup.py` | Журнал, QApplication, экран запуска, фоновая подготовка VLC, открытие окна и ошибки |
| `src/ui/main_window.py` | Комната, готовность каждого участника, выбор видео, управление и отображение передачи |
| `src/session/state.py` | Состояние комнаты и `PeerState` с медиа, готовностью, RTT, смещением часов и рассинхроном |
| `src/network/connection_manager.py` | WebSocket-соединения, handshake, адресация, рассылка, проверка сессии и роли |
| `src/network/network_thread.py` | asyncio loop в QThread, сигналы Qt, отдельный последовательный worker приёма на диск |
| `src/network/protocol.py`, `messages.py` | Протокол 2, формат JSON, проверка типов, размеров и числовых значений |
| `src/network/file_transfer.py` | Чанки, полный потоковый SHA-256, временный файл, проверка размера и публикация без перезаписи |
| `src/player/vlc_player.py` | Экземпляр libVLC, локальное медиа, готовность декодера и нативный видеовывод |
| `src/media` | SHA-256 всего файла и сравнение метаданных |
| `src/infrastructure` | Пути библиотек, ротация журнала, проверка настоящего VLC через тестовый AVI |
| `src/version.py` | Версия приложения для окна, handshake и проверки тега релиза |

## Запуск и потоки

Сначала создаются QApplication и экран запуска. `StartupWorker` в QThread настраивает пути VLC до импорта python-vlc, загружает компоненты и создаёт экземпляр libVLC. `MainWindow` и все QWidget создаются в GUI-потоке. При ошибке экран скрывается, причина записывается в журнал; интерактивный запуск показывает диалог, проверочный возвращает код 1. Отмена запуска ждёт рабочий поток и освобождает подготовленный VLC.

`NetworkThread` обслуживает собственный asyncio loop. Сетевые события передаются GUI через Qt signals. Отправка файлов и SHA-256 выбранного медиа работают в пуле из трёх потоков. Приём чанков выполняется в отдельном последовательном worker; сетевой обработчик ждёт запись каждого чанка до чтения следующего. `max_queue=4` и лимит 1 МиБ ограничивают входную очередь. Большие base64-чанки не передаются в очередь GUI, только прогресс и результат.

Доступ к VLC при выборе файла и проверке его готовности выполняется в GUI-потоке; SHA-256 считается отдельно. Результат загрузки содержит поколение операции: результаты старого выбора и закрытой комнаты игнорируются. Готовность требует состояния Playing/Paused и положительной длительности; ошибка и таймаут не выставляют `local_ready`.

## Комната и сообщения

Ведущий слушает `0.0.0.0:45892`. Каждая новая комната получает новый ID сессии и шестизначный код. Все принятые соединения хранятся в `clients`, каждому назначается отдельный `peer_id`. Ведомый имеет одно соединение с ведущим.

1. Ведомый отправляет `join` с кодом, именем и версией приложения.
2. Ведущий проверяет протокол и код, отвечает `join_accepted` с ID сессии и участника.
3. Локальное событие `peer_joined` передаётся окну ведущего; оно отправляет текущие сведения о видео и готовности этому участнику.
4. После handshake каждый пакет проверяется по ID сессии, форме payload и роли. Повторный handshake запрещён; до 2048 последних ID используются для дедупликации каждого соединения.
5. Локальное `peer_left` удаляет готовность отключившегося участника, отменяет его передачу и приостанавливает просмотр.

Общий JSON содержит `type`, `protocol_version=2`, `session_id`, `message_id` и `sent_at`. Payload не может перезаписать общие поля. Поля `sender_id` и `received_at` относятся к локальному транспортному контексту и не принимаются от удалённого участника. Локальные события `host_started`, `peer_joined`, `peer_left`, `file_progress`, `file_saved` запрещены в сетевом протоколе.

Отправка без получателя у ведущего — рассылка всем; с `recipient_id` — одному соединению. Pong возвращается именно отправителю ping. Клиентские команды воспроизведения и разрешение несовпадения не исполняются на ведущем. Несовместимый протокол, неверная сессия и некорректные сообщения закрывают соответствующее соединение, сохраняя остальные.

Закрытие комнаты закрывает все сокеты и сервер, отменяет незавершённое подключение и освобождает порт. Асинхронный lock сериализует создание и закрытие комнаты. GUI сбрасывает сессию, медиа, готовность и отменяемые таймеры.

## Готовность и синхронизация

У ведущего отдельные медиа и готовность каждого ведомого. Play/Seek разрешены только при подключении, готовности всех участников, совпадении файлов или разрешении ведущего и отсутствии активной передачи. `not_ready`, смена файла и новый участник отменяют старые команды и приостанавливают просмотр.

Ведущий назначает возрастающий `command_id`, общую позицию и `execute_at` в своих монотонных часах. Задержка составляет 350–1500 мс в зависимости от RTT. Ping/Pong дают оценку RTT и смещения часов; ведомый переводит `execute_at` в свою шкалу. До первой оценки используется относительная задержка с поправкой на половину RTT. Новая команда заменяет предыдущий отложенный таймер; смена комнаты/медиа отменяет его по поколению.

Пауза выполняется на одной будущей позиции у ведущего и ведомых. Коррекция движущегося видео также рассчитывается для будущего момента. При позднем выполнении движущаяся позиция корректируется на величину опоздания. Ведомые отправляют позицию и playing; ведущий учитывает возраст измерения, проверяет расхождение play/pause и отправляет коррекцию конкретному участнику не чаще раза в три секунды. Порог позиции — 400 мс. Команды старше последней рассылки и состояния во время отложенной команды не вызывают коррекцию.

Это оценка для локальной сети, а не гарантия точной аудиосинхронизации: асимметричная задержка, джиттер и декодер влияют на результат.

## Передача файла

`file_offer` содержит UUID передачи, имя, размер, длительность и полный SHA-256. Ведущий выбирает одного получателя; ведомый отправляет ведущему. После подтверждения получатель проверяет свободное место и открывает уникальный `.part` эксклюзивно. Имена очищаются от пути и недопустимых символов, ограничиваются по длине, учитывают зарезервированные имена Windows.

Чанки до 512 КиБ передаются в base64 с порядковым индексом. Размер проверяется до записи, SHA-256 обновляется потоково. Отправитель также пересчитывает SHA-256 и не отправляет успешное завершение для изменившегося исходника. Получатель сверяет размер, заявленный и фактический SHA-256, затем создаёт финальный файл без перезаписи существующего. `file_received` подтверждает проверку отправителю. Отмена и таймаут ожидания 60 секунд очищают передачу; сигналы старого worker проверяются по ID передачи.

Результат открывается как новое локальное медиа. Возобновления и автоматического удаления завершённых копий нет.

## Проверка и выпуск

Зависимости закреплены в requirements-файлах. Windows-пакет собирается на Python 3.12 x64. Перед упаковкой выполняются Ruff и pytest; после неё `--smoke-test` создаёт тестовый AVI средствами Python и проверяет готовность VLC, декодирование, Play/Pause/Seek с фиктивным выводом. Видеокартинка и звук на реальном устройстве проверяются отдельно.

Тесты основного окна используют реальный Qt с заменой VLC. Интеграционные сценарии создают ведущего и два ведомых с настоящими WebSocket-соединениями. [AUDIT.md](AUDIT.md) перечисляет фактически выполненные проверки и ограничения выпуска.
